# Neuromem: A Granular Decomposition of the Streaming Lifecycle in External Memory for LLMs

ICML-2026

**核心一句话**：作者把外部记忆从一个端到端黑盒拆成五个生命周期环节，并用严格按时间推进的插入与检索协议逐项测量准确率和延迟。论文最重要的结论是，存储结构决定可达到的质量上限，许多依赖 LLM 的压缩、维护和检索增强只是在插入端与检索端之间转移计算成本。

---

## Key Contribution

- We introduce Neuromem, an open-source testbed for evaluating External Memory Modules under a streaming protocol within a unified serving stack.
- We propose a granular decomposition of memory architectures into five design dimensions and implement representative design variants for each, enabling precise, controlled ablations.
- We conduct an extensive empirical study across diverse long-horizon benchmarks to distill practical design guidelines on balancing reasoning quality with insertion and retrieval costs.

- **把评测对象从完整系统下沉到生命周期算子**：作者不再直接比较 Mem0、MemoryOS、A-Mem 等完整系统，而是把它们拆成可替换的存储、预处理、维护、查询改写和上下文整合模块。这样可以回答性能提升究竟来自哪个环节。
- **把静态记忆评测改造成状态持续演化的流式评测**：每条事实按时间插入，查询只能访问当时已经写入的内容。评测会在多个中间状态触发，因此可以观察记忆增长后性能如何变化。
- **同时报告质量和系统成本**：作者将插入延迟与检索延迟分开测量，重点分析计算开销被放在哪个阶段，而不是只给最终准确率。
- **给出一组有工程价值的负面结论**：原始文本在多数测试中优于三元组重写，启发式维护优于 LLM 驱动的 CRUD，多查询融合只带来很小的准确率增益，却显著增加实时路径延迟。

> [!tip] 这篇论文真正有价值的地方
> 它提供了一种研究外部记忆的方法论：先统一服务栈，再冻结其他环节，只替换一个生命周期算子。对于高度耦合的 Agent Memory 系统，这种归因式实验比直接比较系统总分更容易形成可复用结论。

> [!warning] 贡献表述需要收紧
> - 论文称五个维度相互正交，但 D1 会直接限制 D2、D3、D4 和 D5 的合理实现。知识图谱通常需要实体或三元组抽取，向量库通常依赖文本切块和嵌入，两者很难完全独立替换。
> - 正文将 Neuromem 称为开源测试床，附录同时写明代码仍在整理并计划后续发布。当前版本更接近可复现框架设计与实验原型。

## Method

### 1. 研究对象：持续演化的外部记忆

**直觉**：真实 Agent 在服务过程中会不断写入新事实，同时回答用户问题。记忆状态始终在变化，因此只在最终状态上查询一次，会掩盖中间阶段的退化和维护成本。

作者把请求流写成：

$$
\mathcal{R}=\{r_i=(\tau_i,\mathrm{TYPE}_i,\mathrm{PAYLOAD}_i)\}_{i=1}^{\infty}
$$

其中：

- $\tau_i$ 表示请求发生的时间。
- $\mathrm{TYPE}_i\in\{\mathrm{INSERT},\mathrm{RETRIEVE}\}$ 表示写入或读取。
- INSERT 的负载是历史上下文 $h$。
- RETRIEVE 的负载是用户查询 $q$。

记忆状态随插入次数变化，记为 $M^{(0)},M^{(1)},\ldots$。这里的上标 $k$ 表示已经完成了多少次插入，并非自然时间步。

#### 插入过程

**直觉**：一条原始历史在进入存储前可能需要切分、摘要或结构化，写入后还可能执行去重、遗忘或图结构更新。

$$
M^{(k)}=
\mathrm{POST}_{\mathrm{INS}}
\left(
M^{(k-1)},
\mathrm{PRE}_{\mathrm{INS}}(h^{(k)})
\right)
$$

- $\mathrm{PRE}_{\mathrm{INS}}$ 对应 **D2 Normalization**，决定原始信息以什么粒度和形式进入记忆。
- 底层写入操作由 **D1 Memory Data Structure** 决定。
- $\mathrm{POST}_{\mathrm{INS}}$ 对应 **D3 Consolidation**，负责冲突处理、遗忘和结构调整。

#### 检索过程

**直觉**：用户问题通常不能直接变成底层索引的查询信号，检索结果也不能总是原样塞给生成模型，因此读取过程还包含查询转换和上下文整理。

$$
c=
\mathrm{POST}_{\mathrm{RET}}
\left(
M^{(k^*)},
\mathrm{PRE}_{\mathrm{RET}}(q)
\right)
$$

- $k^*$ 是当前查询发生前已经完成的最后一次插入。
- $\mathrm{PRE}_{\mathrm{RET}}$ 对应 **D4 Query Formulation**。
- 从 $M^{(k^*)}$ 中查找候选内容的方式由 **D1** 决定。
- $\mathrm{POST}_{\mathrm{RET}}$ 对应 **D5 Context Integration**，将候选证据过滤、重排、合并成最终上下文 $c$。

![[98_Assets/NeuroMem.png]]

图 1 的中心是 D1，因为所有插入和检索操作最终都要落到具体数据结构上。上半部分是写入链路，D2 先决定存什么，D3 再决定存储状态如何演化。下半部分是读取链路，D4 决定如何问，D5 决定如何把查到的内容交给生成模型。

> [!question] 五维分解真的相互正交吗
> 原文把 D1 到 D5 称为正交维度。我注意到这种说法更适合作为工程接口抽象，难以视为严格的算法独立性。图记忆若不做实体关系抽取，很难发挥图结构的优势。三元组重写放到向量检索中，又会天然损失原始语言信息。部分消融实际上测试了模块与存储结构之间的匹配程度。

### 2. 流式评测协议

**直觉**：查询必须看到当时已经发生的历史，同时不能访问未来事实。最直接的实现方式是严格按照时间戳串行执行插入和检索。

作者先按 $\tau_i$ 对全部请求排序。处理规则如下：

1. 收到 INSERT 时，完成 D2、D1 写入和 D3 维护，得到新的 $M^{(k)}$。
2. 到达评测检查点时，暂停后续历史流。
3. 在当前稳定状态上执行 D4、D1 检索和 D5。
4. 生成答案并记录 Token-level F1、插入延迟和检索延迟。
5. 评测完成后继续处理下一条历史。

![[98_Assets/NeuroMem-1.png]]

图 5 展示了静态协议和本文协议的核心差异。静态协议一次性写入全部历史，只测试最终状态。Neuromem 会在 State1、State2、State3 等多个状态上查询，因此可以测量性能随记忆增长的轨迹。

![[98_Assets/NeuroMem-2.png]]

图 4 给出了实现层结构。`HistorySource` 持续产生历史，`PipelineCaller` 控制插入、检查点和检索，`ExperimentSink` 记录指标。作者使用 backpressure 阻塞历史流，保证一次插入或检索期间记忆状态不会变化。

> [!tip] 严格因果性的实现很干净
> backpressure 让每次查询都对应一个明确的记忆快照，避免异步写入造成结果不可复现。对评测框架而言，这是很实用的设计。

> [!warning] 这里模拟的是串行在线系统
> - 真实部署常把摘要、图更新和冲突消解放入异步后台任务。Neuromem 将这些操作同步放在关键路径上，因此会放大主动维护的用户可见延迟。
> - 检索开始后记忆状态被冻结，论文没有研究并发读写、最终一致性、陈旧读取和锁竞争。
> - 因此，这套协议适合比较同步服务路径，不足以覆盖完整的生产流式系统。

### 3. D1 Memory Data Structure

**直觉**：存储结构决定信息被保留成什么形态，也决定检索阶段能使用哪些访问路径。后续查询改写和重排只能利用已经存下来的信息，无法恢复写入阶段丢失的内容。

作者将结构分成两类：

- **Partitional**：把记忆视为相互独立的单元，通过队列、分段存储、倒排索引、向量索引或摘要缓存进行访问。
- **Hierarchical or Graph**：显式构建实体、关系和链接，通过图遍历或多跳路径进行检索。

代表性实例包括：

| 结构 | 对应实现直觉 | 主要优势 | 主要成本 |
|---|---|---|---|
| FIFO Queue | 只保留近期内容 | 写入简单、延迟低 | 容量受限、历史易丢失 |
| Queue + Segment | 短期队列与分段长期存储 | 时序管理稳定 | 关系推理能力有限 |
| Inverted + Vector | 词法索引与语义索引并用 | 兼顾精确词匹配和语义召回 | 索引构建与维护更重 |
| Summary + Vector | 摘要缓存与向量库结合 | 压缩上下文 | 摘要可能丢失细节 |
| Semantic KG or Property Graph | 显式关系结构 | 支持多跳和关系检索 | 抽取、更新和遍历成本高 |

![[98_Assets/NeuroMem-3.png]]

图 2 将 Token-level F1 与结构本身的延迟放在同一坐标系中。LoCoMo 和 LongMemEval 上，`Inverted+Vector` 位于效率前沿附近，说明双索引带来的延迟能转化为更高召回。MemoryAgentBench 的 Selective Forgetting 更强调频繁状态更新，轻量队列结构反而更有优势。

论文给出的纵向结果也很关键：

| 结构 | R1 F1 | R5 F1 | 退化幅度 |
|---|---:|---:|---:|
| FIFO Queue | 0.169 | 0.094 | -44.4% |
| Queue + Segment | 0.395 | 0.338 | -14.4% |
| Inverted + Vector | 0.411 | 0.358 | -12.9% |

作者据此提出 **Storage Architecture Dictates Performance Bounds**。更准确的理解是：在他们测试的共同服务栈中，D1 对最终性能的解释力明显高于 D2 到 D5 的局部增强。

> [!warning] 对普遍规律的表述过强
> - 论文将记忆增长后的下降称为普遍规律和固有时间熵。三个数据集和有限结构只能支持稳定观察到的退化趋势，尚不足以建立普遍定律。
> - D1 的完整跨数据集验证较充分，D2 到 D5 的完整消融主要集中在 LoCoMo。后续四个维度的结论没有同等强度的跨任务支持。
> - Figure 2 比较的是作者在统一框架中的结构实例，不能直接视为原始 MemoryOS、Mem0 或 A-Mem 完整系统的排行榜。

### 4. D2 Normalization Strategy

**直觉**：写入前的处理需要在可索引性和信息保真度之间取舍。结构越紧凑，检索越容易定向；压缩过程也越可能删除时间、语气和上下文限定。

作者比较三种策略：

- **None**：直接保存原始文本。
- **Enrich**：生成摘要或补充标签。
- **Rewrite**：把对话改写成三元组或原子事实。

关键结果如下：

| 后端 | 策略 | R1 F1 | R5 F1 | 插入延迟 |
|---|---|---:|---:|---:|
| Queue + Segment | None | 0.371 | 0.325 | 146 ms |
| Queue + Segment | Enrich | 0.369 | 0.324 | 580 ms |
| Queue + Segment | Rewrite | 0.171 | 0.112 | 1552 ms |
| Property Graph | None | 0.347 | 0.301 | 1171 ms |
| Property Graph | Enrich | 0.380 | 0.300 | 2567 ms |
| Property Graph | Rewrite | 0.163 | 0.113 | 4491 ms |

作者的核心判断是 **Semantic Compression is Lossy**。三元组抽取会删除自然语言中的时间标记、指代、限定条件和事件上下文，导致后续检索只能看到经过裁剪的事实骨架。

![[98_Assets/NeuroMem-4.png]]

图 7 进一步拆开写入延迟。`Rewrite` 的主要成本发生在存储之前，三元组抽取本身接近 2 秒。换用 E5-Large 后，原始文本的 Mean F1 为 0.319，三元组版本只有 0.129，同时总插入延迟从 1171 ms 增加到 4497 ms。

> [!tip] 这里的负面结果很有启发性
> 很多记忆方法默认结构化等于更干净。本文说明，结构化首先是一种信息瓶颈。抽取器输出的字段集合、数量上限和表达能力决定了系统以后还能看到什么。

> [!warning] 原始文本严格更优的结论受任务和实现限制
> - LoCoMo 主要通过自然语言问答评测，答案依赖对话细节和时间表达，这类任务天然偏好保留文本纹理。
> - Rewrite 在默认设置中限制三元组数量，Qwen-Plus 验证也只放宽到 10 条。性能下降可能同时来自抽取容量不足、模式设计不完整和检索器不匹配。
> - 论文没有在真正依赖关系约束、符号更新或精确冲突检测的任务上证明原始文本持续占优。
> - 因此，结果更适合解读为粗粒度三元组重写不适合直接替代原始文本，而非结构化记忆整体无效。

### 5. D3 Consolidation Policy

**直觉**：记忆持续增长会产生重复、冲突和过期内容。维护策略需要控制状态规模和一致性，同时避免每次写入都触发昂贵的生成操作。

作者将维护方式分成三类：

- **Conflict Resolution**：使用 LLM 执行创建、读取、更新和删除操作。
- **Decay Eviction**：根据遗忘曲线、热度或容量规则淘汰内容。
- **Structure Enrichment**：给图记忆增加链接或调整拓扑。

代表性结果：

| 后端 | 策略 | Mean F1 | 维护延迟 |
|---|---|---:|---:|
| Property Graph | None | 0.300 | 小于 1 ms |
| Property Graph | CRUD | 0.301 | 3777 ms |
| Property Graph | Forgetting | 0.303 | 120 ms |
| Queue + Segment | None | 0.341 | 小于 1 ms |
| Queue + Segment | CRUD | 0.342 | 1983 ms |
| Queue + Segment | Decay Eviction | 0.342 | 61 ms |

作者据此认为，在线流式场景中启发式维护具有更好的效用与延迟比。这里的重点很明确：CRUD 可能改善语义一致性，但当前问答 F1 几乎没有反映这种收益，数秒维护成本却直接进入同步写入路径。

> [!question] 评测指标是否看得到维护策略的真正价值
> 冲突消解和可控遗忘的目标常包括状态一致性、事实新鲜度、隐私删除和容量约束。本文主要使用答案 Token-level F1，难以检查旧事实是否被物理删除、冲突状态是否被正确修复、记忆规模是否受控。

> [!warning] 隐私结论缺少直接实验证据
> 论文在影响声明中强调启发式遗忘有利于隐私合规，这个判断在机制上合理，但实验没有测量删除完整性、残留召回率或可验证擦除。当前结果只证明它延迟低，并未完成隐私层验证。

### 6. D4 Query Formulation Strategy

**直觉**：同一个问题可以直接做向量检索，也可以先提取关键词、判断是否需要访问记忆，或拆成多个子问题。改写的目标是让查询信号更适合底层索引。

作者比较：

- **None**：直接对原查询编码或检索。
- **Validate**：先判断是否需要访问记忆。
- **Keyword**：提取关键词后检索。
- **Decompose**：用 LLM 把复杂问题拆成子查询。

Queue + Segment 上的结果最能说明问题：

| 策略 | Mean F1 | Query Formulation 延迟 |
|---|---:|---:|
| None | 0.341 | 161 ms |
| Keyword | 0.099 | 1117 ms |
| Decompose | 0.328 | 2209 ms |

关键词抽取删除了原问题中的关系和上下文，导致准确率显著下降。问题分解保留了更多语义，但额外生成步骤让延迟增加十倍以上，平均 F1 仍低于直接检索。

> [!warning] Generative Query Formulation 的范围过宽
> - 论文测试的是特定 prompt、模型和聚合方式。查询分解是否有效高度依赖子查询质量、去重策略、检索深度和最终证据融合。
> - `Keyword` 的明显失败说明当前实现与底层检索器不匹配，也可能说明关键词抽取过度压缩。它不能代表所有稀疏检索或混合查询改写策略。
> - 论文没有系统扫描 top-k、子查询数量和延迟预算。作者也承认超参数组合过多，因此这里应理解为默认配置下的成本画像。

### 7. D5 Context Integration Mechanism

**直觉**：检索器返回的是候选片段，生成模型需要的是有限、连贯且相关的上下文。整合阶段可以简单拼接，也可以过滤、重排、补充或生成新的查询再检索。

作者比较：

- **None**：直接使用候选结果。
- **Augment**：用低成本启发式补充或整理上下文。
- **Multi-query**：生成多个查询，汇总多个检索结果。

默认模型下，Property Graph 的 Mean F1 在 None 和 Multi-query 中都是 0.299，但后者增加约 1700 ms 的整合延迟。换成 Llama-3-8B 后，Multi-query 从 0.296 提升到 0.303，延迟从 205 ms 增加到 1327 ms。

![[98_Assets/NeuroMem-5.png]]

图 8 把这个差异画得很直接。平均 F1 的绝对增益约为 0.007，总代价增加 6.5 倍，其中约 1125 ms 来自生成式上下文整合。作者因此把它称为 **Latency Tax**。

> [!tip] 这个结论区分了能不能提升和是否值得部署
> 更强模型确实能从 Multi-query 中获得稳定的小幅收益，说明方法并非完全无效。实时服务的关键问题是这点收益是否值得占用一秒以上的关键路径。

> [!warning] 延迟税是部署条件相关的结论
> 离线分析、高价值检索和允许并行调用的系统可能愿意交换延迟换准确率。本文的判断主要适用于同步对话、严格响应时间和单轮生成开销较高的环境。

### 8. 生命周期成本守恒

**直觉**：复杂性通常不会消失，只会被提前到插入阶段，或延后到查询阶段。

论文用五个维度说明这种成本转移：

- D2 做摘要或三元组抽取，会提高每次写入成本，希望降低后续检索难度。
- D3 做冲突消解，会在写入后支付维护成本，希望获得更稳定的状态。
- D4 做查询分解，会在每次读取前支付生成成本，希望提高召回。
- D5 做多查询融合，会在读取后支付整合成本，希望提高上下文质量。
- D1 的结构复杂度同时影响写入、维护和读取。

![[98_Assets/NeuroMem-6.png]]

图 3 使用 F1 per second 展示 D2 到 D5 在五轮中的成本效果轨迹。原始或启发式策略大多保持较高的性价比，依赖 LLM 的策略常落在低性价比区域。

> [!note] F1 per second 的意义
> 这个指标试图把答案质量和响应时间放到一个数值中。它适合观察工程效率，但会把准确率与延迟按固定比例绑定。不同应用对延迟的容忍度差异很大，因此它更适合用作可视化辅助，不宜直接作为统一优化目标。

## Experiments

### 数据集与流式改造

- **LoCoMo**：包含多会话双人对话和证据标注。作者按时间串联对话，并在支持证据已经写入后触发问题。
- **LongMemEvalOracle**：原任务通常是长历史加最终问题。作者把多个独立任务串成连续时间线，在不同位置插入测试点。
- **MemoryAgentBench Selective Forgetting**：只选取需要更新事实和忽略旧知识的子集，用于测试动态一致性和遗忘。

> [!warning] 数据改造会改变原任务分布
> - LoCoMo 在证据写入后立即触发查询，有利于保证因果性，但可能减少长时间保留压力。
> - LongMemEval 通过拼接独立任务制造长流，不同任务之间缺少真实用户长期交互中的语义关联。
> - MemoryAgentBench 只使用 Selective Forgetting 子集，D1 在该数据集上的结论更偏向高频更新环境。

### 指标与平台

- 答案质量：带 Porter stemming 的 Token-level F1。
- 系统成本：Insertion Latency 与 Retrieval Latency。
- 默认嵌入模型：BAAI/bge-m3。
- 鲁棒性嵌入模型：intfloat/e5-large-v2。
- 默认生成模型：pangu embedded 1b，运行于 Ascend 910B。
- 鲁棒性模型：Llama-3.1-8B-Instruct，运行于 Nvidia A6000。
- 评分异步执行，避免评测模型干扰被测流水线延迟。

> [!note] Token-level F1 的局限
> 它能够稳定比较答案词面重叠，计算成本低，适合大规模实验。时间推理、同义改写、事件顺序和否定关系可能得到偏低或失真的分数。论文观察到时间类问题最难，但没有使用专门的时间一致性指标定位错误来源。

### 五个主要发现

1. **Temporal degradation**：多数结构随轮次推进而下降，简单 FIFO 退化最严重。
2. **Storage structure sets the frontier**：混合倒排与向量结构在推理型任务上形成较好的质量延迟前沿。
3. **Aggressive normalization loses information**：三元组重写显著损害自然语言记忆问答。
4. **Generative optimization adds critical-path latency**：查询分解和多查询融合收益有限，延迟通常增加一个数量级。
5. **Heuristics are competitive online**：遗忘曲线、热度迁移和简单增强在实时约束下比 LLM 维护更实用。

### Ablation Study 的真正信息

这篇论文的消融价值主要来自以下三点：

- **信息一旦在 D2 丢失，后续模块无法补救**。Rewrite 失败说明存储前的信息瓶颈比检索后的优化更危险。
- **昂贵生成操作需要在对应阶段产生可测收益**。CRUD、Decompose 和 Multi-query 的共同问题是成本明确，收益接近噪声水平。
- **结构与工作负载存在匹配关系**。推理密集型数据偏好多索引结构，高频更新数据偏好轻量结构，单一最优记忆架构并不存在。

### 整体实验漏洞

> [!warning] 需要谨慎解读的地方
> - D1 在三个数据集上交叉验证，D2 到 D5 的主要结论集中在 LoCoMo，结论覆盖范围不对称。

> - 单一 Token-level F1 难以覆盖冲突修复、遗忘正确性、状态规模、隐私删除和证据完整性。

## Future

### 作者明确提出的方向

- 定义短期工作记忆与长期存储的边界，并研究分层维护策略。
- 构建能够检查中间记忆状态的数据集，减少只看最终答案的局限。
- 对图记忆采用异步抽取和严格增量式更新，避免每次写入扫描全局图。
- 继续优化完整的 insert、maintain、retrieve、integrate 生命周期。

### 值得继续挖掘的研究方向

#### 1. 从独立维度消融走向算子交互建模

五个阶段之间存在明显耦合。可以把实验对象扩展为 D1 与 D2、D1 与 D4、D3 与 D5 的兼容性矩阵，研究什么结构需要什么归一化和查询接口。最终目标是学习一套 **operator compatibility model**，预测某种模块组合是否会发生信息损失或延迟爆炸。

#### 2. 以状态正确性补充答案 F1

可以直接测量记忆状态：

- 当前事实是否可检索。
- 已过期事实是否仍能被检索。
- 冲突事实是否保留正确版本。
- 删除请求后是否存在残留。
- 每条答案能否追溯到正确证据。

这类指标能让 D3 的维护价值被直接观察。

#### 3. 加入真实并发与一致性协议

未来测试床需要覆盖异步写入、后台 consolidation、并发查询、版本化快照和陈旧读取。此时评测目标会从单次延迟扩展到吞吐量、尾延迟、状态新鲜度和一致性。

#### 4. 让生命周期策略适应工作负载

论文已经观察到推理型任务偏好多索引结构，高频更新任务偏好轻量队列。下一步可以根据写入速率、查询类型、时间预算和记忆规模动态选择：

- 是否进行摘要或结构化。
- 是否触发冲突消解。
- 使用多少检索分支。
- 选择哪个索引或记忆层。

这会把固定记忆流水线变成成本约束下的策略决策问题。

#### 5. 研究可逆或保真结构化

Rewrite 的失败说明单向压缩风险很高。更合理的设计可以同时保留原始证据和结构化视图，结构化单元只承担路由作用，最终回答仍回到原文证据。这样既能利用关系索引，也能避免三元组成为唯一信息载体。

#### 6. 将延迟预算写进优化目标

可以把质量、插入成本、检索成本和状态规模写成统一目标：

$$
\max_{\pi}
\mathbb{E}[Q]
-\lambda_{\mathrm{ins}}C_{\mathrm{ins}}
-\lambda_{\mathrm{ret}}C_{\mathrm{ret}}
-\lambda_{\mathrm{mem}}C_{\mathrm{state}}
$$

其中 $\pi$ 是生命周期策略，$Q$ 是回答或状态质量，三个 $\lambda$ 由具体应用的服务等级目标决定。这里比单独最大化 F1 per second 更灵活，因为不同系统可以明确设置写入与读取成本的权重。

---

## Final Takeaway

这篇论文没有提出新的外部记忆算法，它建立了一套拆解和评测记忆算法的方法。最值得保留的核心直觉有三点：

1. **存储阶段的信息损失具有不可逆性**，检索增强无法稳定补回已经被摘要或结构化删除的细节。
2. **生成式维护与检索增强需要单独核算关键路径成本**，方法有效不等于适合在线部署。
3. **记忆架构必须与工作负载匹配**，推理深度、更新频率和延迟预算共同决定合理结构。

我认为论文最强的部分是统一服务栈下的负面消融，最薄弱的部分是把有限实验趋势提升为普遍规律。Neuromem 适合作为后续记忆系统研究的实验骨架，但还需要状态级指标、算子交互实验和并发协议，才能覆盖真正的长期 Agent Memory 生命周期。
